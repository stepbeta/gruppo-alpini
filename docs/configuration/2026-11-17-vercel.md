## 1. Why it is configured this way

Three constraints drive everything below.

1. **The service key must never reach a browser.** Vercel has no per-variable "server-only" toggle;
   the *only* mechanism is the absence of the `NEXT_PUBLIC_` prefix. Every variable is therefore
   named deliberately, and the privileged key is marked Sensitive so its value cannot be read back.
2. **Previews must not touch production data.** The application talks to Supabase directly from the
   browser, so a preview deployment with production variables is an unauthenticated write path into
   member records. Previews are disabled until a second Supabase project exists.
3. **Latency and data residency follow the database.** Supabase is `eu-west-2` (London), so
   functions run in `lhr1`.

## 4. Rebuild from scratch

Prerequisites: the repo on `main`, a Supabase project, and the three values from Supabase
(Project Settings → API).

### 4.1 Import the project

Vercel → Add New → Project → import `stepbeta/gruppo-alpini`. Framework is detected as Next.js; no
build or output override is needed. Deploy once so the project exists.

### 4.2 Environment variables

Settings → Environment Variables. Add exactly three, **Production** only:

```bash
cd ~/experiments/gruppo-alpini
vercel link                      # select the existing project, or create it
vercel env add NEXT_PUBLIC_SUPABASE_URL production
vercel env add NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY production
vercel env add SUPABASE_SECRET_KEY production --sensitive
```

Rules:

- The privileged key must never be named with a `NEXT_PUBLIC_` prefix.
- Use `--sensitive` for the privileged key. Sensitive values cannot be revealed or pulled
  afterwards — that is the point, and it is a one-way door.
- Do not add `SUPABASE_JWT_SECRET`, `POSTGRES_*`, or any `SUPABASE_ANON_KEY` alias. Nothing in the
  codebase reads them, and the JWT secret alone is enough to forge any session.
- If a Supabase integration is installed, prefer disconnecting it and declaring the three variables
  by hand; otherwise it re-injects a dozen unused credentials.

### 4.3 Deployment Protection

Settings → Deployment Protection → **Standard Protection** (Vercel Authentication for all
deployments except production custom domains). Leave Password Protection off and create no bypass
tokens.

### 4.4 Region and previews

Both come from `vercel.json` and need no dashboard action:

```json
{ "regions": ["lhr1"], "git": { "deploymentEnabled": { "**": false, "main": true } } }
```

The dashboard's Function Region dropdown is overridden by this file. Keep one source of truth: the
file.

### 4.5 Domains

Settings → Domains. Attach the production host and confirm it resolves with `200` and a valid
certificate. If a custom domain is attached, add it to Supabase Auth redirect URLs in the same
change.

### 4.6 Runtime environment settings

Settings → Environment Variables → untick **Enable access to System Environment Variables**.

### 4.7 Deploy and verify

```bash
vercel --prod                      # or merge to main and let the Git integration deploy

curl -sI https://gruppo-alpini-ten.vercel.app/ | grep -iE "x-frame|x-content|referrer|permissions|content-security"
curl -sI https://gruppo-alpini-ten.vercel.app/ | grep -ci strict-transport      # expect 1

TOKEN=$(jq -r .token ~/.local/share/com.vercel.cli/auth.json)
PID=$(jq -r '.projects[0].id' .vercel/repo.json)
curl -s -H "Authorization: Bearer $TOKEN" "https://api.vercel.com/v9/projects/$PID" \
  | jq '{ssoProtection: .ssoProtection.deploymentType, autoExposeSystemEnvs}'
curl -s -H "Authorization: Bearer $TOKEN" "https://api.vercel.com/v6/deployments?projectId=$PID&limit=1" \
  | jq -r '.deployments[0] | "\(.target) \(.state)"'
```

Preview policy check: push any branch and confirm **no** deployment appears for it, then delete the
branch.

## 5. Operating rules

1. **Production is deployed from `main` by the Git integration.** `vercel --prod` deploys any
   working tree and bypasses GitHub branch protection entirely; use it only for an emergency and
   re-deploy `main` immediately afterwards.
2. **Exactly three environment variables.** A fourth is a finding until proven otherwise. No secret
   may carry a `NEXT_PUBLIC_` prefix.
3. **Previews stay off** until a dedicated Supabase project exists.
4. **Do not duplicate HSTS** in `next.config.ts`; Vercel already sends it.
5. **Never commit a Vercel token.** Tokens are account-wide and cannot be scoped, so they are not
   suitable for CI or for handing to a tool.
6. **`.vercel/` is gitignored** and per-machine; it is not configuration.

## 6. Traps discovered

- **A variable with no dots and no eye icon is Sensitive, not empty.** There is no reveal path.
  Verify functionally (delete a throwaway account) rather than visually.
- **`vercel env pull` returns nothing for Sensitive variables.** `.env.local` must keep the real
  privileged key by hand.
- **`git.deploymentEnabled` uses minimatch, and `*` does not cross `/`.** `"*": false` leaves every
  `feature/x` branch deploying while appearing to disable previews. Use `"**"`. When a branch
  matches several rules, one `true` wins — that is what keeps `main` deploying.
- **Vercel already emits HSTS with `preload`.** Adding a second HSTS header in the app yields
  duplicates; the platform value is the stronger one.
- **Standard Protection protects deployment URLs, not production domains.** Any
  `<project>-<team>.vercel.app` deployment host answers `302` to `vercel.com/sso-api`, so it must
  never be used as an auth `Site URL` or redirect target.
- **`regions` in `vercel.json` overrides the dashboard dropdown.** Editing both creates silent
  disagreement.
- **An empty Preview environment is safe by accident, not by design.** It only looks harmless
  because the missing variable makes the Supabase client `null`; copying production variables in
  would quietly create a write path into real data.
