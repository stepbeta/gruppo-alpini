## 0. Production launch blockers

The portal is not ready for real members until these two exist. They are one dependency, not two: a
custom domain is what makes SMTP possible, and SMTP is what makes account recovery possible.

| Blocker | Why it blocks launch |
| --- | --- |
| **Custom domain** | Vercel's `*.vercel.app` hosts are not a stable identity. Deployment hosts are SSO-protected and answer `302` to Vercel SSO, so only the production host is usable in an auth callback — and that hostname can change with the project. A member typing the address, and a phisher registering a lookalike `gruppo-alpini-xyz.vercel.app`, both point at the same weakness: no domain the associazione actually controls. Only a custom domain can be added to Google Cloud OAuth and to Supabase's redirect allow-list with confidence. It is also the surface Vercel treats as public production, since Deployment Protection excludes custom domains. |
| **Custom SMTP** | Supabase's built-in mailer is rate-limited and restricted to team-member addresses, so it cannot deliver to members at all. Without SMTP: password recovery is impossible, "Secure email change" (currently enabled) is inert because the confirmation never arrives, magic links and email OTP cannot work, and email confirmation cannot be turned on. The project therefore runs with `mailer_autoconfirm: true`, which means **accounts are never email-verified** — acceptable only because an administrator approves every account. |

Launch checklist, in order:

1. Buy the domain; point it at Vercel (Domains) and confirm HTTPS.
2. Add SPF/DKIM records from the SMTP provider (Resend, Brevo, or equivalent) to that domain.
3. Configure SMTP in Supabase Authentication → Emails.
4. Set Site URL to the custom domain and add it to the redirect allow-list.
5. Add the custom domain to the Google OAuth authorised redirect URIs.
6. Decide whether to enable email confirmation now that it can be delivered.

Until step 6, the approval gate remains the identity control — see §5, rule 5.

## 1. Why it is configured this way

1. **The database is the authorization boundary.** RLS policies, table and column grants, triggers
   and constraints — not the React code — decide who can read or write what. Migrations in
   `supabase/migrations/` are therefore the authoritative security record, and the repository must
   match the deployed database exactly.
2. **The browser talks to PostgREST directly.** Almost every read and write bypasses the Next.js
   server. That makes the publishable key public by design, and puts the entire burden on RLS.
3. **Membership is small and vouched for.** An administrator approves every account, so open
   registration is tolerable and email confirmation is not the identity control. The approval gate
   is.

Not required for launch, worth doing eventually:

- **CAPTCHA / rate limiting (Turnstile or hCaptcha)** on `/login`. Signup is open and auto-confirmed,

## 4. Rebuild from scratch

### 4.1 Project

Create the project in **`eu-west-2`** — the region cannot be changed later without a migration, and
it must match the Vercel function region (`lhr1`).

```bash
npx supabase login
npm run db:link -- --project-ref <REF_ID>
```

### 4.2 Schema

```bash
npm run db:push          # applies supabase/migrations/ in order
npx supabase migration list
```

Never edit an applied migration; add a new file with `npm run db:new <name>`. The database is the
authorization boundary, so a migration whose contents differ from what was reviewed is a security
regression, not a formatting issue.

### 4.3 API keys

Use the new key formats. Publishable keys are public; secret keys are server-only.

- Browser and Vercel: `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` → `sb_publishable_…`
- Server and Vercel (Sensitive): `SUPABASE_SECRET_KEY` → `sb_secret_…`
- Disable the legacy `anon` / `service_role` keys once nothing uses them. User session tokens are
  unaffected: they remain JWTs signed with the project JWT secret, which is a separate credential
  from the legacy API keys.

### 4.4 Auth

Authentication → URL Configuration:

- **Site URL**: the production domain only. Never a `*.vercel.app` deployment host — those are
  behind Deployment Protection and answer `302` to Vercel SSO.
- **Redirect URLs**: exact pairs only, for example
  `http://localhost:3000/**` and `https://<production-host>/**`. No wildcards across hosts.
- **Email confirmations off** is acceptable *only* because the approval gate exists. If an
  administrator stops reviewing accounts, turn confirmations on and configure SMTP in the same
  change.

Providers: Google (client ID + secret, callback registered in Google Cloud Console) and Email.
Password requirements: minimum length 12, no composition rules.

### 4.5 SMTP

Required before real members can recover access:

1. Own a domain with SPF/DKIM (a shared sender address only delivers to the account owner).
2. Resend or Brevo free tier → verify the domain → copy DNS records.
3. Authentication → Emails → SMTP: host, port 465, username, API key as password, sender address.

### 4.6 Verify

```bash
npx supabase migration list                     # local == remote
npx supabase db advisors                        # local; warns it targets local by default
npm run db:reset && npm run test:integration    # 63 RLS/grant/trigger assertions
```

Production smoke test: sign in, list the member directory, submit a request, delete a throwaway
account (exercises the secret key → `auth.admin.deleteUser`).

## 5. Operating rules

1. **Migrations are the source of truth.** Local and remote must match; run `migration list` after
   every push.
2. **Run the integration suite before `db:push`.** It is the only automated proof that grants,
   restrictive policies and triggers still deny what they should.
3. **The secret key never leaves the server.** No `NEXT_PUBLIC_` prefix, never in CI, never in a
   client component.
4. **The advisor baseline is 7 security warnings**, each explained in §2. Anything new is a finding.
5. **Approval, not email, is the identity control.** `email_confirmed_at` proves an address was
   reachable, not that a person is a member.
6. **Never use a deployment hostname** in the Site URL or redirect list.

## 6. Traps discovered

- **`mailer_autoconfirm: true` means no confirmation email is sent at all.** Silence at signup is
  the configured behaviour, not an SMTP failure. Check the flag before debugging mail.
- **The built-in mailer only delivers to project team members.** It looks configured and silently
  does nothing for everyone else.
- **`CREATE FUNCTION` grants `EXECUTE` to `PUBLIC`.** Every `SECURITY DEFINER` function is callable
  through `/rest/v1/rpc/` until revoked, even if nothing in the UI calls it.
- **Trigger functions still fire after `REVOKE`.** `EXECUTE` is not checked on trigger invocation,
  so revoking is safe for `handle_new_user` and the guard triggers.
- **Policy helpers must stay executable by `authenticated`.** RLS expressions run as the caller;
  revoking them breaks the policy matrix rather than hardening it.
- **Deployment URLs are SSO-protected, production domains are not.** Under Standard Protection,
  `<project>-<hash>-<team>.vercel.app` redirects to Vercel login while the production domain serves
  normally.
- **`supabase db advisors` targets the local database.** Use `--linked` or accept that it reflects
  the local schema; the Management API `/advisors/security` reflects the deployed project.
- **The Free plan cannot enable leaked-password protection.** Don't read the advisor as actionable
  until the plan changes.
