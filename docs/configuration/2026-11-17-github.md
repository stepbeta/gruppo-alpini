# GitHub security audit — 2026-11-17

Repository: `stepbeta/gruppo-alpini` · Plan: GitHub Free · Visibility: **public** (changed today)

Covers repository-level controls only. Vercel and Supabase are separate audits.

---

## 1. Why the repository is public

Branch protection and rulesets were not misconfigured — they were unavailable. On GitHub Free a
**private** repository has no branch protection, no rulesets, and no secret scanning. Verified:

```
GET /repos/stepbeta/gruppo-alpini/rulesets                    -> 403
GET /repos/stepbeta/gruppo-alpini/branches/main/protection    -> 403
"Upgrade to GitHub Pro or make this repository public to enable this feature."
```

`branches/main.protected` was `false`, so `main` had no force-push block, no PR requirement and no
required checks, while migrations reach production from a laptop via `npm run db:push`. The only
review gate between a policy edit and a production RLS change was git review, and git review was
unenforced.

Going public unlocks, at no cost: rulesets on `main`, secret scanning, push protection, CodeQL,
private vulnerability reporting, and unmetered Actions minutes (relevant because the RLS
integration job spends up to 30 minutes on a Docker stack).

Pre-public checks that passed: no secrets in the full git history (only placeholders), no tracked
binaries or screenshots, `.env.local` never committed, `.gitignore` covers `/node_modules`,
`/.next/`, `/coverage`, `/playwright-report/`, `/test-results/`, `.env*.local`. `docs/audits/` and
`gaps.md` were never tracked, so no internal findings were published.

### 4.6 Branch ruleset

The workflow must exist first: required check contexts are job `name:` values, so a renamed job
silently blocks every PR.

```bash
cat > /tmp/ruleset.json <<'EOF'
{
  "name": "main ruleset",
  "target": "branch",
  "enforcement": "active",
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "pull_request", "parameters": {
        "allowed_merge_methods": ["squash", "merge"],
        "dismiss_stale_reviews_on_push": true,
        "require_code_owner_review": false,
        "require_extra_approval_for_unattributed_changes": true,
        "require_last_push_approval": false,
        "required_approving_review_count": 0,
        "required_review_thread_resolution": true,
        "required_reviewers": []
    } },
    { "type": "required_status_checks", "parameters": {
        "do_not_enforce_on_create": false,
        "strict_required_status_checks_policy": true,
        "required_status_checks": [
          { "context": "Typecheck, lint and unit tests" },
          { "context": "Database RLS integration tests" }
        ]
    } }
  ]
}
EOF
gh api -X POST repos/stepbeta/gruppo-alpini/rulesets --input /tmp/ruleset.json
```

No `bypass_actors` are set, so the ruleset applies to administrators too. To relax the
up-to-date requirement (each `main` move otherwise forces a 30-minute integration re-run on every
open PR):

```bash
gh api -X PATCH repos/stepbeta/gruppo-alpini/rulesets/<id> \
  -f 'rules[3][parameters][strict_required_status_checks_policy]=false'
# or PATCH with the full JSON and only that value changed
```

### 4.7 Pin actions and enable the policy

`ci.yml` pins `actions/checkout@11d5960a326750d5838078e36cf38b85af677262`,
`actions/setup-node@49933ea5288caeca8642d1e84afbd3f7d6820020`,
`actions/upload-artifact@ea165f8d65b6e75b540449e92b4886f43607fa02` (all `v4` tips).

Enforce **after** the pinned workflow is on `main`, otherwise tag-pinned workflows fail to start
and block the very PR that fixes them.

`PATCH` on this endpoint returns `404` for this repository; use `PUT` with a JSON body:

```bash

gh api -X PUT repos/stepbeta/gruppo-alpini/actions/permissions --input /tmp/pin.json
gh api repos/stepbeta/gruppo-alpini/actions/permissions   # sha_pinning_required: true
```

### 4.10 Commit signing (SSH)

Signed commits are enforced by the `required_signatures` rule. SSH signing is used rather than GPG:
no key server, no expiry ceremony, and `git` 2.34+ is the only requirement.

```bash
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
git config --global tag.gpgsign true

# lets `git log --show-signature` verify locally, independently of GitHub
mkdir -p ~/.config/git
printf '%s %s\n' "$(git config user.email)" "$(cat ~/.ssh/id_ed25519.pub)" \
  > ~/.config/git/allowed_signers
git config --global gpg.ssh.allowedSignersFile ~/.config/git/allowed_signers
```

Register the **public** key on GitHub as a **signing** key: `Settings → SSH and GPG keys → New SSH
key → Key type: Signing Key`. The same key may be registered twice, once for authentication and
once for signing. The API equivalent (`POST /user/ssh_signing_keys`) requires the
`admin:ssh_signing_key` token scope, which a default `gh auth login` does not request.

Verify before enabling the rule — a signed test commit must come back `valid`:

```bash
git switch -c test/signature-check
git commit --allow-empty -m "chore: verify ssh commit signing"
git log -1 --format='%h %G?'          # expect G
git push -u origin test/signature-check
gh api repos/stepbeta/gruppo-alpini/commits/$(git rev-parse HEAD) \
  --jq '.commit.verification | {verified, reason}'   # expect true / valid
```

Only then add `{ "type": "required_signatures" }` to the ruleset. GitHub re-evaluates existing
commits when a key is registered, so a commit that reported `unknown_key` flips to `valid` without
being re-pushed.

Squash merges performed in the UI are created and signed by GitHub, so enforcement does not block
merging from the web interface; it blocks unsigned commits pushed directly by a client.

## 5. Operating rules

1. **No direct pushes to `main`.** `git push origin main` is rejected. Flow: branch → push → PR →
   checks → squash merge. No bypass actors exist, so even the owner cannot override.
2. **`main` runs CI twice by design**: `pull_request` (pre-merge gate) and `push` (post-merge
   backstop). PR branches are no longer double-run.
3. **Renaming a CI job renames its required check.** Update the ruleset in the same PR or every PR
   blocks forever.
4. **Never commit `docs/audits/` or `gaps.md`.** Both are gitignored and must stay untracked.
5. **CI must never receive a Supabase service key.** Integration tests use the local stack and
   `supabase status` credentials only. If a cloud project is ever needed in CI, put the value in a
   `production` Environment with required reviewers, never a repo-level secret.
6. **Any change to `.github/workflows/**` or `supabase/migrations/**` is a security change** — it
   is the only thing standing between a typo and a production RLS regression.
7. **Workflows must reference actions by full commit SHA.** Tag refs no longer start once pinning is
   enforced, so a Dependabot major bump that arrives as `@v8` must be re-pinned to a SHA in the PR.
8. **Commits on `main` must be signed.** Local commits are signed by the SSH key configured in
   §4.10. An unsigned commit is rejected on push; fix it with `git commit --amend -S --no-edit`, or
   for a range: `git rebase --exec 'git commit --amend -S --no-edit' <base>`.

## 6. Traps discovered

- **`PATCH /repos/{owner}/{repo}/actions/permissions` returns `404`.** The documented `PATCH`
  method, with or without `sha_pinning_required` in the body, fails on this repository. `PUT` with
  the same JSON body returns `204` and applies the change. Do not conclude "no permission" from the
  `404` — check the method first.
- **Two rulesets AND together.** Both were briefly active (one created in the UI, one by script).
  Duplicated `required_status_checks` rules do not conflict visibly — they silently accumulate the
  strictest combination. Keep exactly one branch ruleset.
- **Ruleset API needs public or Pro.** A private repo on Free returns `403` from every ruleset and
  classic-protection endpoint. This is a plan gate, not a permissions problem.
- **`gh repo edit` has no `--accept-visibility-change-consequences`.** That flag belongs to
  `gh repo create`; use the REST `PATCH` for non-interactive visibility changes.
- **`security_and_analysis` returns `null`** when no GHAS feature is available. That is a plan
  signal, not an API bug.
- **`GET /repos/{owner}/{repo}/vulnerability-alerts`** returns `204` when Dependabot alerts are on
  and `404` when off — the status is the payload.
- **A key registered only for authentication does not verify commits.** The same key must be added a
  second time with *Key type: Signing Key*, otherwise the commit is correctly signed but GitHub
  reports `unknown_key`. Registering the key re-verifies existing commits retroactively — a
  `verified: false` commit becomes `verified: true` without being re-pushed, which makes it a safe
  pre-flight check before enabling the rule.
- **`git log --format=%G?` shows `N` even for a correctly signed commit** until
  `gpg.ssh.allowedSignersFile` is configured. Local verification and GitHub verification are
  independent; the GitHub API's `commit.verification` field is authoritative for enforcement.
- **The signing-key API needs a scope `gh auth login` does not request.** `POST /user/ssh_signing_keys`
  returns `404` without `admin:ssh_signing_key`; the UI equivalent is `Settings → SSH and GPG keys`.
- **`require_code_owner_review: true` with `CODEOWNERS` = `* @stepbeta`** makes every PR
  unmergeable for a solo owner. Keep it `false` until a second reviewer exists; scope
  `CODEOWNERS` to `/supabase/migrations/` and `/.github/workflows/`.
- **Undoing public exposure is incomplete.** Forking is enabled on public repos and forks survive a
  later re-privatisation. History, including the `d428726` Gmail author address, is already
  crawlable.
